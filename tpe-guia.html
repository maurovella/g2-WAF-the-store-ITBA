Detalle por Tema

01
Gestión de Infraestructura por Código
Terraform · Pulumi
Complejidad: Media Industria: Muy Alta Utilidad: Alta
▾

¿De qué trata?

En lugar de configurar servidores y clusters manualmente o con scripts de bash, IaC permite describir toda la infraestructura en archivos de código versionables. Si alguien borra el cluster por error, con un solo comando se recrea idéntico. Es la diferencia entre "yo lo armé a mano una vez" y "cualquiera puede replicarlo exactamente".

Plan Básico

  • Instalar Terraform o Pulumi
  • Escribir código que defina el cluster Kind local (o en la nube: EKS/GKE)
  • Declarar cada recurso de Kubernetes: Deployments, Services, Secrets, ConfigMaps
  • Aplicar con terraform apply y ver cómo levanta todo solo
  • Demostrar destruir y recrear el entorno completo desde cero

Ejemplo Concreto

Hoy existe local.sh create-cluster que hace todo a mano con scripts. Con Terraform, habría un archivo main.tf donde se declara "quiero un cluster con estos 5 servicios y estas variables de entorno" y Terraform se encarga del resto — además de trackear el estado y detectar si algo cambió.

Utilidad Personal

Alta

Terraform es de las skills más pedidas en cualquier puesto que no sea puramente frontend. Si alguna vez desplegás un proyecto propio en AWS, GCP o DigitalOcean, IaC te ahorra horas de configuración manual. Para equipos chicos es especialmente valioso porque no hay un DevOps dedicado — el mismo dev que escribe código también levanta la infra.

Aporte al Proyecto The Store

Hoy el proyecto depende de local.sh y de que quien lo levante tenga todo instalado correctamente. Con IaC, cualquier integrante (o el docente evaluando) podría reproducir el entorno completo con un solo comando, sin importar la máquina. Además, si el proyecto escalara a la nube, el mismo código Terraform que levanta el cluster local podría apuntar a AWS EKS o GCP GKE sin reescribir nada. The Store pasaría de ser "un proyecto que corre en mi máquina" a "un proyecto que corre en cualquier lugar de forma reproducible".
02
Observabilidad con Zabbix
Zabbix Server · Agent · Proxy
Complejidad: Media Industria: Media Utilidad: Baja-Media
▾

¿De qué trata?

Zabbix es una plataforma de monitoreo que permite saber en todo momento si los sistemas están funcionando correctamente. Cuando un servicio se cae o la CPU se dispara, Zabbix lo detecta y puede enviar alertas. Es como tener un vigilante 24/7 mirando todos los servicios.

Plan Básico

  • Desplegar Zabbix Server dentro del cluster (o en una VM aparte)
  • Instalar Zabbix Agent en cada nodo del cluster
  • Configurar Zabbix Proxy si hay múltiples nodos
  • Crear items de monitoreo para los 5 servicios: chequeo HTTP, CPU/RAM, latencia
  • Configurar triggers y alertas ("si Cart no responde en 30s, alertar")

Ejemplo Concreto

Si el servicio checkout se cae y nadie está mirando, los usuarios no pueden comprar y nadie lo sabe hasta que alguien se queja. Con Zabbix, a los 30 segundos de caerse ya hay una alerta en pantalla (o email/Telegram) diciendo "Checkout DOWN en el cluster".

Utilidad Personal

Baja-Media

Zabbix es sólido pero orientado a entornos corporativos grandes con equipos de operaciones dedicados. Para proyectos propios o equipos chicos, el stack de Grafana (tema 3) es mucho más moderno, flexible y usado. Vale aprender los conceptos de monitoreo, pero Zabbix como herramienta específica es poco probable que lo uses fuera de contextos enterprise o infraestructuras legacy.

Aporte al Proyecto The Store

The Store actualmente no tiene ningún sistema de alerta si algo falla. Con Zabbix, cada uno de los 5 microservicios tendría un monitor de disponibilidad activo. Si durante la demo el pod de cart se cae por falta de memoria, Zabbix lo detecta en segundos — convirtiendo un problema embarazoso en una demostración del valor del monitoreo. También permitiría ver en tiempo real el consumo de recursos de cada servicio durante el load test que ya incluye el proyecto.
03
Observabilidad con Grafana
Prometheus · Loki · Tempo · Grafana
Complejidad: Media Industria: Muy Alta Utilidad: Muy Alta
▾

¿De qué trata?

El stack de Grafana es el estándar moderno de observabilidad en microservicios. Combina tres pilares: métricas (Prometheus), logs (Loki) y trazas distribuidas (Tempo), todo visualizado en Grafana. Permite entender no solo si algo falló, sino por qué y en qué parte del flujo.

Plan Básico

  • Desplegar Prometheus, Loki, Tempo y Grafana vía Helm charts
  • Configurar Prometheus para scraping de métricas de cada pod
  • Configurar agentes de Loki para capturar logs de todos los contenedores
  • Instrumentar algún servicio con trazas (ej. Checkout → Orders)
  • Armar dashboards mostrando req/s, latencia P99 y tasa de errores

Ejemplo Concreto

Un usuario reporta que el checkout tarda mucho. Con Tempo podés ver la traza completa del request: UI tardó 5ms, Catalog tardó 8ms, pero Orders tardó 2 segundos. Inmediatamente sabés dónde está el problema sin revisar logs de cada servicio por separado.

Utilidad Personal

Muy Alta

Este stack es el estándar de la industria y lo vas a encontrar en prácticamente cualquier empresa tech moderna. Es open source, gratuito, y se usa tanto en startups de 3 personas como en empresas grandes. Para proyectos propios con usuarios reales, detectar un bug en producción antes de que los usuarios se quejen es invaluable. Es la skill de observabilidad más transferible que podés aprender hoy.

Aporte al Proyecto The Store

The Store tiene 5 servicios que se comunican en cadena: UI → Catalog, UI → Cart → Orders → Checkout. Sin observabilidad, ese flujo es una caja negra. Con Grafana se volvería completamente transparente: dashboards mostrando req/s por servicio, latencia bajo carga, errores en la cadena. Durante el load test (local.sh load-test), se podría ver en tiempo real cómo cada servicio responde al estrés y dónde aparece el cuello de botella primero.
04
Acceso Remoto Seguro
OpenVPN · WireGuard · Tailscale · EasyRSA
Complejidad: Media Industria: Media Utilidad: Media
▾

¿De qué trata?

Una VPN crea un túnel cifrado entre dos redes. En vez de exponer el cluster de Kubernetes a internet abierto, solo los clientes conectados a la VPN pueden acceder a los servicios internos. Es el mecanismo que usan las empresas para que los empleados accedan a sistemas internos desde sus casas.

Plan Básico

  • Levantar el cluster de The Store en una VM (VirtualBox o nube)
  • Instalar OpenVPN o WireGuard en esa VM como servidor VPN
  • Generar certificados con EasyRSA (OpenVPN) o claves (WireGuard)
  • Conectar desde otra máquina como cliente VPN
  • Demostrar que desde fuera de la VPN no se puede acceder, y desde dentro sí

Ejemplo Concreto

The Store corre en una VM con IP privada 192.168.1.50. Sin VPN, hay que exponer el puerto 80 a internet. Con WireGuard, el compañero de grupo se conecta a la VPN desde su notebook, obtiene IP virtual 10.0.0.2, y accede a The Store como si estuviera en la misma red — sin exponer nada al exterior.

Utilidad Personal

Media

Entender VPNs te da una base sólida de networking. WireGuard en particular es moderno, simple y muy usado. Lo más práctico para proyectos propios es Tailscale (basado en WireGuard), que conecta tus servidores y dispositivos en una red privada en minutos. Si alguna vez tenés un servidor propio o trabajás con infra remota, vas a cruzarte con esto.

Aporte al Proyecto The Store

The Store actualmente solo corre en localhost. Con VPN implementada, el cluster podría correr en una VM centralizada del equipo y cada integrante accedería de forma segura desde su notebook. Para la presentación final, la demo podría correr en un servidor remoto y los docentes accederían via VPN — en lugar de depender de que una sola notebook funcione bien el día de la exposición.
05
Gestión Centralizada de Logs
Elasticsearch · Logstash · Kibana · Fluentd · Beats
Complejidad: Alta Industria: Alta Utilidad: Media
▾

¿De qué trata?

En microservicios, cada servicio genera sus propios logs. Buscar un error implica entrar a cada contenedor por separado. ELK centraliza todos los logs en un solo lugar con búsqueda poderosa. Es como tener el grep de todos los servicios a la vez, con filtros, gráficos y búsqueda full-text.

Plan Básico

  • Desplegar Elasticsearch (almacenamiento), Logstash/Fluentd (recolección) y Kibana (visualización)
  • Configurar Fluentd como DaemonSet para capturar logs de todos los pods automáticamente
  • Crear índices por servicio: ui-logs, catalog-logs, orders-logs, etc.
  • Armar dashboards en Kibana con filtros por nivel (ERROR, WARN, INFO)
  • Demostrar búsqueda: "todos los errores de Orders en los últimos 10 minutos"

Ejemplo Concreto

El servicio orders lanza una excepción Java a las 3am. Con ELK, a la mañana siguiente buscás en Kibana level:ERROR AND service:orders y ves el stack trace completo — sin necesidad de entrar al pod, que quizás ya se reinició y el log desapareció.

Utilidad Personal

Media

Los conceptos detrás de ELK son muy valiosos y Elasticsearch aparece mucho (búsqueda full-text, analytics). Sin embargo, para proyectos propios o equipos chicos ELK puede ser pesado de mantener — consume mucha RAM. En la práctica, para esos casos conviene Loki (tema 3) que es más liviano. Dicho eso, en una empresa mediana-grande, es casi seguro que te crucés con ELK.

Aporte al Proyecto The Store

The Store tiene 3 servicios Java (UI, Cart, Orders), uno en Go (Catalog) y uno en Node.js (Checkout) — cada uno con su propio formato de logs. Sin ELK, depurar un flujo completo de compra implica correr kubectl logs en 5 pods distintos y correlacionar manualmente los timestamps. Con ELK, todos esos logs quedan en Kibana con formato unificado y buscable. Para la demo, se podría ejecutar el load test, generar intencionalmente un error en un servicio, y mostrar cómo aparece instantáneamente en Kibana sin tocar ningún pod.
06
Despliegue y Gestión del Cluster
Ansible · K3s · Kind · Minikube · kops
Complejidad: Media-Alta Industria: Muy Alta Utilidad: Alta
▾

¿De qué trata?

Kubernetes es poderoso pero complejo de instalar y configurar correctamente. Este tema trata sobre automatizar esa instalación y gestión: preparar las VMs, instalar dependencias, crear el cluster y desplegar las aplicaciones. Ansible permite hacer esto de forma reproducible en cualquier máquina con playbooks declarativos.

Plan Básico

  • Tener dos VMs (master + worker) o usar Kind/K3s en local
  • Escribir Ansible Playbooks: instalar Docker, kubectl, configurar el cluster
  • Aplicar el kubernetes.yaml de The Store automáticamente desde el playbook
  • Con un solo comando ansible-playbook deploy.yml levanta todo
  • Demostrar escalado: agregar un worker node y ver cómo K8s redistribuye los pods

Ejemplo Concreto

Hoy, para levantar The Store en una máquina nueva hay que instalar Docker, Kind, kubectl, clonar el repo y correr local.sh. Con Ansible, el playbook hace todo eso automáticamente en cualquier máquina Linux con un solo comando. El docente podría levantar el mismo entorno en su notebook sin instalar nada manualmente.

Utilidad Personal

Alta

Kubernetes es el estándar para despliegue de aplicaciones y aprenderlo bien es una inversión que vale mucho. K3s es ideal para proyectos propios — es Kubernetes completo pero liviano, corre en una Raspberry Pi o en un VPS de 1GB RAM. Ansible también es muy útil para automatizar la configuración de cualquier servidor, no solo Kubernetes.

Aporte al Proyecto The Store

El proyecto ya usa Kind con local.sh, pero ese script es frágil — si falta una dependencia o la versión de Docker difiere, falla sin mensaje claro. Con Ansible, el setup se vuelve idempotente: podés correrlo 10 veces y siempre queda el mismo resultado correcto. Con K3s en lugar de Kind, el cluster se comporta más parecido a producción real. Para la demo, se podría mostrar un cluster multi-nodo real donde los 5 servicios están distribuidos entre nodos, y Kubernetes los balancea automáticamente.
07
CI/CD
GitHub Actions · Jenkins · Helm · CodePipeline
Complejidad: Baja-Media Industria: Muy Alta Utilidad: Muy Alta
▾

¿De qué trata?

CI/CD automatiza el proceso de llevar código nuevo a producción. Cada vez que alguien hace un git push, el pipeline automáticamente construye la aplicación, corre los tests y la despliega. Elimina el "funciona en mi máquina" y reduce errores humanos en el deploy.

Plan Básico

  • El proyecto ya tiene .github/workflows/main.yml — extenderlo
  • Agregar build de imágenes Docker para los 5 servicios y push a GHCR/Docker Hub
  • Agregar los tests E2E automáticos (ya existen con local.sh e2e-test)
  • Empaquetar los servicios en Helm Charts y hacer deploy automático al cluster
  • Demostrar: push en vivo → GitHub Actions construye, testea y despliega solo

Ejemplo Concreto

Se cambia el precio de un producto en el Catalog. Sin CI/CD: buildear la imagen manualmente, subirla al registry, actualizar el deployment en Kubernetes. Con CI/CD: git push, el pipeline lo hace todo en 3 minutos y el cambio está en el cluster automáticamente.

Utilidad Personal

Muy Alta

Esta es probablemente la skill más inmediatamente útil para un dev independiente o de equipo chico. GitHub Actions es gratis para repos públicos, increíblemente flexible y está integrado en la herramienta que ya usás. Tener un pipeline que automáticamente corra tests y haga deploy cada push es algo que podés aplicar desde mañana en cualquier proyecto propio. Es lo que todas las empresas dan por sentado que sabés.

Aporte al Proyecto The Store

El proyecto ya tiene .github/workflows/main.yml pero básico. Extenderlo con un pipeline completo transformaría The Store en un proyecto con flujo de desarrollo profesional real: cada cambio en cualquiera de los 5 servicios dispara automáticamente el build, los tests E2E, y el deploy al cluster con Helm. Para la demo, el momento más impactante sería modificar un texto en la UI en vivo, hacer push, y en 3 minutos mostrar ese cambio corriendo en el cluster — sin haber tocado nada manualmente.
08
Service Mesh & API Gateway
Kuma · Kong Community · Envoy
Complejidad: Alta Industria: Alta Utilidad: Media-Alta
▾

¿De qué trata?

Un Service Mesh agrega una capa de infraestructura que gestiona la comunicación entre microservicios: cifrado automático (mTLS), reintentos, circuit breakers y observabilidad de tráfico interno. Kong como API Gateway controla el tráfico externo: autenticación, rate limiting, routing inteligente.

Plan Básico

  • Instalar Kuma en el cluster como control plane del service mesh
  • Inyectar el sidecar proxy (Envoy) en cada pod de The Store automáticamente
  • Configurar políticas: mTLS entre servicios, timeout de 5s para Checkout, circuit breaker en Orders
  • Instalar Kong como Ingress Controller del cluster
  • Configurar rate limiting y demostrar que bloquea el exceso de requests

Ejemplo Concreto

Sin service mesh, si el servicio orders se cae, los requests desde checkout simplemente fallan hasta timeout. Con Kuma y circuit breaker configurado, después de 5 fallos consecutivos devuelve error inmediato sin esperar — protegiendo al resto del sistema de la cascada de fallos.

Utilidad Personal

Media-Alta

Kong como API Gateway es muy útil incluso para proyectos chicos: autenticación, rate limiting y routing sin programarlo. El service mesh en cambio es más relevante cuando tenés muchos microservicios — para proyectos propios suele ser overkill. Aprender los conceptos vale, pero probablemente no lo implementes en proyectos pequeños.

Aporte al Proyecto The Store

The Store tiene exactamente el tipo de arquitectura donde un service mesh brilla: 5 microservicios que se comunican entre sí sin ningún control ni visibilidad sobre ese tráfico interno. Kuma agregaría mTLS automático entre todos los servicios (actualmente hablan en HTTP plano), circuit breakers para que si orders se satura no arrastre a checkout, y un dashboard de tráfico mostrando el flujo UI → Cart → Orders → Checkout en tiempo real. Kong reemplazaría el Ingress actual con políticas de rate limiting, demostrable con el load generator del proyecto.
09
Protección con WAF
ModSecurity · Shadow Daemon · OWASP CRS
Complejidad: Media Industria: Media Utilidad: Baja-Media
▾

¿De qué trata?

Un WAF (Web Application Firewall) analiza el contenido de los requests HTTP y bloquea ataques web conocidos: SQL Injection, XSS, path traversal, etc. Se ubica delante de la aplicación web y filtra el tráfico malicioso antes de que llegue al servidor.

Plan Básico

  • Desplegar ModSecurity como módulo de Nginx/Apache frente al servicio ui
  • Activar el OWASP Core Rule Set (CRS) con reglas para los ataques más comunes
  • Configurar en modo "detection" primero (solo loguea) y luego "blocking"
  • Demostrar ataques bloqueados: XSS en el buscador, path traversal en la URL
  • Mostrar los logs registrando los intentos bloqueados con código 403

Ejemplo Concreto

El buscador de The Store tiene un campo de texto. Sin WAF, un atacante podría ingresar <script>alert('xss')</script> y potencialmente ejecutar código en el browser de otros usuarios. Con ModSecurity activado, ese request es bloqueado con 403 antes de llegar a la UI de Spring Boot.

Utilidad Personal

Baja-Media

Entender cómo funciona un WAF te hace mejor developer porque te hace pensar en seguridad. Sin embargo, ModSecurity es complejo y para proyectos propios casi siempre hay soluciones más simples (Cloudflare WAF gratuito hace lo mismo con cero configuración). Lo más valioso de este tema es el conocimiento del OWASP Top 10 en sí mismo — eso sí lo aplicás al escribir código seguro en cualquier proyecto.

Aporte al Proyecto The Store

La UI de The Store es una aplicación Java/Spring Boot con formularios (búsqueda, carrito, checkout) que actualmente no tiene ninguna protección a nivel de red contra ataques web. ModSecurity agregaría esa capa de defensa perimetral. Para la demo, el aporte es especialmente visual: se puede mostrar el mismo ataque antes y después del WAF — primero el <script> llega a la app, luego con ModSecurity activo es cortado con 403 y queda registrado en los logs.
10
Security Scanning
OpenVAS · Greenbone GSE · GVM-Tools · ospd-openvas
Complejidad: Media Industria: Media-Alta Utilidad: Media
▾

¿De qué trata?

Un escáner de vulnerabilidades analiza sistemas buscando debilidades conocidas: puertos abiertos con servicios vulnerables, versiones de software con CVEs conocidos, configuraciones inseguras. OpenVAS/Greenbone es el estándar open source para este tipo de auditoría. Es lo que usaría un pentester o equipo de seguridad antes de poner un sistema en producción.

Plan Básico

  • Desplegar Greenbone/OpenVAS en una VM separada (~4GB RAM mínimo)
  • Configurar GVM-Tools para automatizar los escaneos via CLI
  • Apuntar el escáner contra los servicios expuestos del cluster de The Store
  • Ejecutar un escaneo completo y analizar el reporte: CVEs, severidad, recomendaciones
  • Demostrar cómo actualizar una imagen reduce la cantidad de vulnerabilidades

Ejemplo Concreto

OpenVAS escanea el cluster y detecta que la imagen de catalog usa una versión de Go con una CVE conocida de severidad media, y que Redis está accesible sin autenticación. El reporte muestra exactamente qué parchear — antes del scan nadie sabía que Redis estaba expuesto.

Utilidad Personal

Media

Saber que existen herramientas de scanning y haber corrido una aunque sea una vez te cambia la perspectiva sobre la seguridad. Para proyectos propios, herramientas como Trivy (escaneo de imágenes Docker) o Snyk son más accesibles y se integran directo en el pipeline de CI/CD — y son mucho más usadas en el día a día de desarrollo moderno que OpenVAS.

Aporte al Proyecto The Store

The Store tiene 5 servicios con imágenes Docker que nunca fueron auditadas en términos de seguridad. Un escaneo con OpenVAS revelaría el estado real del proyecto: CVEs en las versiones de Java, Go o Node.js usadas, configuraciones expuestas innecesariamente, puertos abiertos que no deberían estarlo. El aporte más valioso para la demo sería mostrar el ciclo completo: escaneo inicial → reporte con vulnerabilidades → aplicar un fix (actualizar una imagen) → segundo escaneo mostrando que las vulnerabilidades desaparecieron.
